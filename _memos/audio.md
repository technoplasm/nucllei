# 音声(STT / TTS)— 構成・内部関数・ハードスケーリング

STT/TTS の fork 側実装と、性能・ハード(強い CPU / 将来 GPU)方針の真実源。
llens 現行の実機構成は `_links/llens` の `stt/README.md` / `tts/README.md`。
内部関数の設計経緯は #53、ファイル処理との関係は `file-handling.md`。

## 有効/無効(配備レベルの機能フラグ)

`ENABLE_AUDIO_STT` / `ENABLE_AUDIO_TTS`(persist: `audio.stt.enable` / `audio.tts.enable`、既定 on、
admin Settings > Audio にトグルあり)。off にすると **FE のアイコン(マイク / 読み上げ / Call)非表示 +
`/transcriptions`・`/speech` が 403**(サーバー側 enforcement)。#66 で廃止した per-user 権限フラグ
(誰に使わせるか)とは別物 — こちらは「この配備に機能があるか」。Call は STT+TTS 両方を使うので
どちらか off で非表示。内部関数(`utils/audio.py`)はこのフラグを見ない(caller = admin 作の tool/filter
の責務。エンジン未設定なら既に ValueError)。

## 構成(2026-07-13 現在)

- **STT**: `AUDIO_STT_ENGINE=""` = 内蔵 faster-whisper(**fork プロセス内**で CTranslate2 推論)/
  `"openai"` = 外部 OpenAI 互換 API。llens 現行 = 内蔵 large-v3-turbo・int8・CPU。
  faster-whisper は extras `stt`(torch 無しで軽い — Docker イメージに同梱)。
  dev では `uv sync --extra stt` か `--extra local-ml` で入る(2026-07-16 の extras 分割)。
- **TTS**: `AUDIO_TTS_ENGINE="openai"` = OpenAI 互換(llens = tts-bridge → AivisSpeech)。
  fork プロセスは合成しない(プロキシ + mp3 キャッシュのみ)— fork 側の CPU/GPU 設定と無関係。
- **内部関数(#53)**: `utils/audio.py::transcribe_audio / synthesize_speech`。
  sync 提供(主 caller = sync tool。async からは `asyncio.to_thread`)。
  TTS の voice/model は config 既定 + 引数上書き、en/ja→voice の対応表は caller(prism 層 tool)責務。

## 逐次文字起こし(疑似ストリーミング)と読み取り猶予(#56、2026-09-04)

録音バー(`src/routes/(app)/chat/MessageInput/VoiceRecording.svelte`)は完全バッチ
(stop 時に 1 blob を投げる)をやめ、**発話の区切りごとに転写して入力欄へ追記**する。

- **切り方(確定の単位)**: timeslice のチャンク単位では確定しない。webm/opus は先頭チャンクに
  しかヘッダが無く、2 個目以降が単体でデコードできないため。**無音の切れ目か周期の切れ目(次節)で
  MediaRecorder を stop → すぐ次のセグメントを起こす**(CallOverlay の `stopRecordingCallback` と同じ形)。
  timeslice は使わない。
- **無音検出**: 波形表示と同じ rAF ループで AnalyserNode(`minDecibels` = -45)+ `lastSoundTime`。
  外部 VAD ライブラリは入れない(オフライン配備で CDN / モデル DL を持ち込まない制約)。
  音を検出したところで `MediaRecorder.start()`(無音だけのセグメントを作らない)。
- **転写**: 既存の `transcribeAudio()`(`POST /api/v1/audio/transcriptions`)のまま。
  新エンドポイント・WebSocket は作らない(socket.io は撤去済み — `streaming-wire-v2.md`)。
- **順序保証**: チャンクは**直列 Promise キュー**(`transcribeQueue`)に積む。
  並列に投げると順不同で追記され文が壊れる。確定ボタンも同じキューの最後尾に乗るので、
  途中チャンクの追記が終わってから `onConfirm` が走る(二重挿入・順序逆転が構造的に起きない)。
- **親への渡し方**: 途中の区間は `onTranscript({text})`(入力欄へ追記するだけ)、
  最後の 1 区間だけ `onConfirm({text, send})`(追記 + 録音 UI を閉じる)。`send` は録音バーの
  **「ここで切って送信」ボタン**(チェック = 入力欄へ入れるだけ、の隣)で、親は追記したうえで
  そのまま `onSubmit` する(送るものが無ければ送らない。書き込み側の無かった設定 `speechAutoSend` は #122 で撤去)。
- **表示**: 録音中は入力欄が録音バーに置き換わって見えないので、確定済みテキストを
  バー内にも出す。先頭に録音開始時点の書きかけ(`draft` prop = 親の `prompt` のスナップショット、
  薄色)、続けてこの録音で足した分(通常色)— 「書きかけの末尾に足される」のが見て分かるように
  (ken 指摘 2026-10-02)。周期の進捗と文字起こし中の表示は次節。
- **トグルは作らない(常時 ON)**: 逐次はバッチの上位互換 — 一度も間を置かずに喋れば
  結果は従来と同一(1 チャンク)。トグルを付けると使われない 2 本目の経路が残るだけで、
  fork の「互換のためだけのコードを残さない」規律に反する。可変にする価値があるのは
  下の「読み取り猶予」の方なので、そちらを設定に出した。
- **キャンセルの意味**: 既に入力欄へ入ったテキストは残る(送信済みの確定分)。
  飛行中の転写結果は破棄する(`aborted`)。
- **後始末は `onDestroy` が持つ**: `recording` を false にするのは親の onCancel / onConfirm
  だけなので、ルート遷移でコンポーネントが破棄されると `recording` は true のまま残る。
  `onDestroy` で `stopRecording()`(トラック停止・`AudioContext.close()`・interval clear・
  recorder 停止)まで確実にやる。rAF ループの継続判定も `recording` prop ではなく
  `aborted` を見る — でないと破棄後もループが回り、無音の切れ目ごとに転写を投げ続けて
  マイクインジケータが点きっぱなしになる(2026-09-05 修正)。
- **stop() と発話再開のレース**: `MediaRecorder.stop()` は同期で state を `inactive` に
  するが `onstop` は後から来る。この窓で喋り直すと rAF ループが同じ recorder を
  `start()` し直してしまうため、**`stopping` を見て起こさない**。起こすと直前の発話が
  捨てられ、古い recorder が残り、共有している `audioChunks` に別ストリームのチャンクが
  混ざって壊れた webm になる(2026-09-05 修正)。
- **キューは必ず解決状態へ戻す**: `transcribeQueue` を 1 度でも reject させると以後の
  `.then` が全部スキップされ、確定しても `finish()` が呼ばれず録音バーがスピナーのまま
  固まる。末尾に `.catch()` を置き、最終セグメントで落ちたときは `finish('')` で必ず閉じる。
- **STT 障害時のトーストは 1 録音につき 1 回**。切れ目ごとに出すと積み上がる。

### 周期確定と進捗表示(2026-10-02。同日の interim 方式を置き換え)

無音の切れ目(既定 4 秒)まで何も出ないと、喋っている本人は「どこまで読み取れたか」が
分からない(ken 指摘)。**喋り続けていても一定の周期でセグメントを切り、その分だけを転写して
確定テキストとして足す**。周期は録音バーに進捗として見せる。

- **切り方**(`SEGMENT_*`、rAF ループ。目安秒と息継ぎ長は配備ごとに env で動かせる — 下の
  「配備ごとの調整」。以下は既定値での説明): セグメントを録り始めてから **12 秒(SOFT = 周期の目安)を
  過ぎたら、次の息継ぎ(400ms の無音)で切る。息継ぎが無くても 16 秒(HARD = SOFT + 4 秒)で切る**。
  読み取り猶予(無音 4 秒)での区切り・確定ボタン・「ここで切って送信」は従来どおり。
  値は下の「周期の実験」で決めた(2026-10-02 夜に 8 / 12 秒から変更)。**速さより安定性
  (区切りで文が壊れないこと)を取る**(ken 決定)。
  - 12 秒: 8 秒 → 12 秒で区切り起因の破綻が約半分になる。16 秒は 12 秒より良くならず遅れだけ増える。
    4 秒は破綻が倍。代償は発話から表示までの遅れ(平均 13.5 → 17.4 秒)。
  - 16 秒: 強制切りは語の途中に当たり、4〜5 割で文が壊れる(息継ぎ切りは 1 割前後)。SOFT から
    息継ぎを待つ猶予が 4 秒。喋った音は遅くとも 16 秒後には転写に回る。
  - 400ms: 句読点・息継ぎの間(概ね 300〜700ms)と語中の無音(促音・破裂音の閉鎖、150ms 未満)の
    間に置いた値。実験でも動かしていない(300ms の扱いは下の未確認事項)。
  - 下限側の制約: 内蔵 CPU STT の転写は 1 回 4〜6 秒で、音声長によらずほぼ一定(下の実測)。周期が
    それより短いと直列キューが溜まる一方になる。
- **切った直後は音を待たずに次を録り始める**(`resumeAfterCut`): 通常のセグメントは音を検出した
  フレームで `start()` するが、周期の切れ目は発話の途中なので、それだと検出 → start の遅れぶん
  次の語頭が欠ける(実測: 息継ぎで切った直後の "We advised" が "Badvised" になった。`onstop` で
  即 `start()` するようにして解消)。そのあと音が来なければ発話区間 0 で、転写には送られない。
- **表示**(録音バー、外部 STT 経路のみ):
  - 進捗バー: 全長が HARD、目盛りが SOFT。目盛りまでは indigo(「聞き取り中 — 区切りごとに文に
    なります」)、目盛りを過ぎたら amber + 点滅(「次の息継ぎで区切ります」)。録っていない間は
    空(「発話を待っています」)。
  - 「文字起こし中」+ スピナー: 転写キューに未完了がある間(`pendingSegments`)。2 件以上なら件数。
  - 確定した文は通常色で足され、足された瞬間だけ背景を薄く光らせる(1.6 秒でフェード)。
- **実機での切れ目**(2026-10-03、SOFT 12 / HARD 16。dev = large-v3-turbo / int8 / CPU、Playwright +
  Chrome の fake マイクに flite の英語音声。`,/voice-check/check12.py`、状態は 250ms 間隔で観測):
  文の間に 0.7 秒の息継ぎがある音声は、セグメント開始から**約 13.6 / 12.8 / 13.2 秒**
  (12 秒を過ぎて最初の息継ぎ)で切れ、切れ目なしの音声は**約 16 秒**で切れた。進捗バーの目盛りは 75%
  (= 12 / 16)。転写は 4.3〜4.7 秒/回のものと 12.6〜14.7 秒かかったものがあり(後者は 8 / 12 秒の
  ときにも出ていた。原因は未調査 — `WHISPER_LANGUAGE=ja` に英語音声を入れたことによる temperature
  fallback の可能性がある)、遅い転写が続いた間はキューが 2 件まで溜まり、追いついて解消した。
  英語音声を `ja` 固定で転写しているので、この確認の認識結果そのもの(切れ目なし音声の 1 本目が
  「ご視聴ありがとうございました」になった等)は精度の評価に使えない。精度は下の実験で見た。
- **Web Speech 経路**: 周期・進捗表示は無い(ブラウザが区切る)。`interimResults = true` で、
  `isFinal` の結果だけを確定に積み、それ以外を未確定(薄色)で後ろに出す — ブラウザが返すもので
  追加コストが無いので残している。**ブラウザでの実機確認は未実施**。

#### 周期の実験(日本語音声、2026-10-02)

置き場所: `,/voice-cut-exp/`(書き捨て。スクリプト一式と `out/report.txt` / `out/segstats.txt`)。
日本語の TTS 音声(文の間に息継ぎあり 14 本 / 切れ目なし 10 本、話速 3 段)と人間の朗読 4 本を、
録音バーと同じ規則(SOFT を過ぎたら 400ms の息継ぎで切る / SOFT + 4 秒で強制切り)で切って
セグメントごとに転写し、**切らずに転写した結果と比べて区切りの前後で文が壊れた箇所**(置換・脱落・
重複・挿入・幻聴。句読点だけの差は数えない)を数えた。dev と同じ large-v3-turbo / int8 / CPU。

| SOFT / HARD | 破綻/分 息継ぎあり(TTS + 朗読) | 破綻/分 切れ目なし | 遅い話者(息継ぎあり) | 破綻率 息継ぎ切り | 破綻率 強制切り | 発話 → 表示の遅れ 平均 / 最大 |
| ----------- | ------------------------------ | ------------------ | -------------------- | ----------------- | --------------- | ----------------------------- |
| 4 / 8 秒    | 1.82                           | 3.13               | 1.60                 | 12% (21/176)      | 49% (49/100)    | 10.1 / 12.0 秒                |
| 8 / 12 秒   | 0.91                           | 1.99               | 1.44                 | 9% (10/106)       | 47% (29/62)     | 13.5 / 16.0 秒                |
| **12 / 16 秒** | **0.50**                    | **1.25**           | **0.32**             | 9% (6/65)         | 35% (17/48)     | 17.4 / 20.0 秒                |
| 16 / 20 秒  | 0.59                           | 1.15               | 0.48                 | 16% (9/57)        | 50% (15/30)     | 20.9 / 24.0 秒                |

(破綻/分・破綻率は report.txt の「基準 = 切らない転写」・prompt なしの行を、息継ぎ切り + 強制切りで
足したもの。破綻率は 3 群の合計。遅れは「TTS 息継ぎあり」群で、転写 1 回 4.0 秒・直列キューでの**試算**
— 実際の転写時間で測ったものではない。)

- **壊れるのは強制切り**: 息継ぎで切った箇所の破綻は 1 割前後、強制切りは 4〜5 割。周期を伸ばして
  効くのは、強制切りに当たる回数が減るから。
- **8 → 12 秒で約半分**: 息継ぎあり 0.91 → 0.50 件/分、切れ目なし 1.99 → 1.25。特に遅い話者 —
  8 秒だと SOFT から 4 秒の間に息継ぎが来ずに強制切りに当たる(1.44 → 0.32)。
- **16 秒は 12 秒より良くならない**(0.59 / 1.15)のに遅れは 3.5 秒増える。**4 秒は破綻が倍**。
- **代償は遅れ**: 発話から表示まで平均 13.5 → 17.4 秒(最大 16 → 20 秒)。STT の占有率は
  約 43% → 約 30% に下がる(同じ試算)。

**未確認事項**:

- **入力レベル依存**: 息継ぎの検出は AnalyserNode の `minDecibels = -45` に対する相対なので、
  入力レベルで切れ方が変わる。実験では音声を -10dB にすると強制切り率が 19% → 3% に下がり、
  -20dB では何も録れなかった。実マイク(AGC あり)でどのレベルになるかは見ていない。
- **実マイク・口述は未測定**: 音声は TTS と朗読で、言いよどみ・言い直しのある実際の口述ではない。
- **息継ぎ長 300ms**: 強制切りを 19% → 8% に減らす(SOFT 8 / HARD 12、TTS 息継ぎあり)が、
  語中の短い無音で切れる害を確かめていないので 400ms のまま。

#### 捨てた方式: 直前の確定文を initial_prompt として渡す(2026-10-02 に実装し、同日中に撤去)

セグメントを 1 つずつ単独で転写すると、区切りをまたいで表記(漢字・専門用語・数字)が揃わず、
文の途中で切れたときのつながりも悪い。そこで**直前までの確定文(書きかけ + この録音で確定した分の
末尾 200 文字)を Whisper の prompt として渡す**実装を入れた(`/transcriptions` の Form `prompt` →
faster-whisper の `initial_prompt` / OpenAI 互換 STT の同名フィールド)。一般には定石で、OpenAI の
ガイドも、分割した音声では前区間の転写結果を prompt に入れるよう勧めている。**この用途では副作用が
勝ったので捨てた**(ken 決定「安定性を重視」)。実装は未コミットのまま外したので履歴には無い。

上の実験と同じ音声で prompt あり / なしを比べた結果(`,/voice-cut-exp/`、`run_prompt.py` と report.txt の
`ip0` / `ip100` / `ip200` 行):

- **破綻率と CER はほぼ変わらない**: SOFT 8 / HARD 12 で破綻/分は息継ぎあり 0.91 → 0.86、
  切れ目なし 1.99 → 1.57。CER の差は 0.2 ポイント以内。
- **良くなるのは句読点・表記の統一だけ**(セグメントごとに句読点の有無が切り替わる回数が
  2.7 → 0.0 回/本)。
- **副作用が危険**:
  - **偽の単位**: prompt に「5mg」「500mg」があると、次のセグメントが「白血球が12000mg、CRPが8.6mg」
    になる。56 run 中、prompt なし 0 件 / あり 7 件。
  - **幻聴**: 1 文字しか入っていないセグメントが「ご視聴ありがとうございました。」になる。
  - **誤りの伝播**: 前のセグメントの誤認識(「死中肺炎」)が次の文脈になり、後続にも同じ誤りが出る。
  - **切れた文の勝手な補完**: 途中で切れた文を、prompt の続きとしてそれらしく埋めてしまう。

読み手が気づきにくい形で数値・単位・病名が変わるので、診療の口述では許容できない。句読点・表記の
不統一は読めば分かり、害が小さい。再検討するなら、prompt に数値・単位を入れない等の対策と、
同じ実験での副作用の再計測が前提。

**API としては任意の `prompt` を受ける**(捨てたのは「マイクの音声入力が直前の確定文を送る」こと
だけ — ken 判断 2026-10-03)。用語リスト等を文脈として渡したい呼び出し元のために、`/transcriptions` の
Form `prompt` と `transcribe(request, file_path, prompt=None)` は残してある: 内蔵 = `initial_prompt` /
`openai` = 同名フィールドで転送 / deepgram・azure は無視。サーバが末尾 200 文字に丸め
(`STT_PROMPT_MAX_CHARS`、Whisper の prompt 枠 224 トークンに対する値)、INFO ログには長さだけ出す。
**マイクの音声入力(`VoiceRecording` / `CallOverlay`)は送らない** — 理由は上記の実験。

#### 捨てた方式: 累積 prefix の再転写(interim、2026-10-02 の数時間だけ存在)

`MediaRecorder.start(1000)` で刻み、**セグメント先頭からの累積チャンク**を発話中に繰り返し
`/transcriptions` へ投げて「未確定テキスト」として薄色で出し、無音 4 秒 or 20/28 秒上限で確定する
方式。single-flight + 空き時間の間引き、確定時の interim 結果の使い回しまで作ったが捨てた。

- **ken の実機所感**(マイクで試用): 「今は 10 秒おきに出るけど、いつその単位が切り上げられるのか
  分からない」「その周期が分かるようになっていると、その周期が切れたら一連の文が入って、
  そのあとまた読み取って、みたいになるから分かりやすい」。毎回先頭から転写し直して未確定文が
  書き換わり続け、いつ確定するのかが見えないのが分かりにくい。
- **実測**: 1 回の転写は音声 7〜14 秒で 4〜6 秒(Whisper は入力を 30 秒窓に詰めるので音声長に
  よらずほぼ一定。0.3 秒の prefix でも約 4〜6 秒)。未確定の更新は約 8〜9 秒おきにしかならず、
  「喋ったそばから出る」にはならなかった。しかも同じ音声を何度も転写するのでサーバ負荷が高い
  (本番は `WHISPER_NUM_WORKERS=1` の直列)。
- 残してある知見 — **累積 prefix はデコードできる**(faster-whisper 1.1.1 + PyAV 12.3.0、
  任意バイト位置で切った prefix): webm/opus(`-live 1`)可 / ogg/opus 可 / fragmented mp4 可 /
  通常の mp4(moov 末尾)不可。GPU / 外部 STT で転写が 1 秒を切るなら interim は再検討に値する。

### 通し録音の添付(2026-10-03)

周期確定は区切りで語が壊れうる(上の実験: 12 / 16 秒でも 0.5〜1.25 件/分)。直すのではなく
**原本を残す**: 区切り用の MediaRecorder とは別に、録音の最初から最後までを録り、その発言の
添付にする。必要なときに配備側(llens)の tool `transcribe_speech(file_id, start_sec, duration_sec)`
が原本から読み直す。**nucllei が持つのは仕組みと事実だけ** — 読み直すかの判断・tool・prompt は
配備側。読み直しは稀なので、普段の音声入力に手間も表示も足さない(ken 決定)。

- **別に録る理由**: 区切りごとのファイルは各自ヘッダを持つので連結できない。
- **形式**: 区切り用と同じ `pickMimeType`(Chrome / Edge / Firefox = webm の Opus、作れない
  ブラウザ = 既定の `audio/mp4`)。mono(`getUserMedia` に `channelCount: 1`)、
  `audioBitsPerSecond = 24000`(既定。`AUDIO_STT_RECORDING_BITRATE_KBPS`)。
- **残すのは区切りが 2 つ以上あった録音だけ**(転写へ送った区間が 2 つ以上)。1 つだけなら
  1 回で文字起こし済みで、読み直しても同じ結果になる — 短い指示の大半はこれで、普段は何も
  付かない。× キャンセルでは何も残さない(アップロードは確定時にまとめて行う)。
- **添付の経路は普通のファイルと同じ**(`POST /files/`、同じチップ、利用者が × で外せる)。
  確定(チェック / 止めて送信)でアップロードし、**完了を待ってから** `onConfirm` する —
  「止めて送信」は添付が付いてから送る。待ちは録音バーの「録音を添付中」。失敗しても文は
  入力欄へ入り / 送信され、トーストで知らせるだけ。待っている間に × を押したら、アップロード
  済みの分も消す。
- **黙って残さない条件**: `chat.file_upload` 権限が無い / 配備の `ATTACHMENT_ALLOWED_EXTENSIONS` に
  その拡張子が無い(`uploads.ts::canKeepRecording`。録音開始時に判定し、通し録音そのものをしない)。
  Web Speech 経路(ブラウザが区切る)も対象外。
- **約 60 分ごとにファイルを分ける**(録音は止めない。利用者には見せない — 経過時間の表示も
  今までどおり)。`FULL_RECORDING_PART_SECONDS`。25MB(`ATTACHMENT_MAX_SIZE` 既定)には約 160 分
  入るのでサイズではなく、**1 本全体の読み直しに実時間の約 1/4 かかる**ことから決めた値。
  配備の添付上限から逆算した時間(2 割の余裕込み)の方が短ければそちらで分ける。
  - 分けるのは **60 分を過ぎた最初の区切り**(息継ぎ / 強制 / 無音)。1 つの区間が 2 つの
    ファイルにまたがらない。発話を待っている間に過ぎたら、その場で分ける。
  - **次の recorder を先に起こし、前は 300ms 遅れて止める**。MediaRecorder は `stop()` した瞬間の
    末尾 40〜50ms を書き出さない(実測)ので、同時に止めると切れ目の直前の音がどちらにも残らない。
    代わりに前のファイルの末尾が次の先頭と約 0.3 秒重なる(区間は重ならない)。
  - 添付数の上限(`ATTACHMENT_MAX_COUNT`、既定は無制限)を超えると、送信時の既存のチェック
    (「一度にチャットで使えるファイルは最大 N 個です。」)で止まる。文とチップは残るので、
    利用者がチップを外して送り直す。
- **印とメタ情報**(llens と合意した契約。正本は `README_API.md` §4.4):
  - `Files.meta.dictation` — `version` / `session_id` / `part` / `parts` / `offset_sec` /
    `duration_sec` / `container` / `segments[{i, start_sec, end_sec, cut, text}]` / `joined_text`。
    秒は**そのファイルの先頭から**(区切り用 recorder を start / stop した時刻)。発話を待っていた
    間は区間の間が空く。`i` は録音全体の通し番号。
  - 受け口は upload の Form `dictation`(JSON)。**クライアントが meta に書けるのはこれだけ**で、
    `routers/files.py::DictationMeta` が形を検証する(未知のキーは拒否・512KB まで・音声のみ)。
  - モデルへ注入する `<source>` には `dictation="true"`(分かれた録音だけ `part` / `parts` も)。
    区間一覧・本文は prompt に入れない。
  - チャット JSON に残るスナップショット(`files[].file.meta`)からは `dictation` を外している
    (本文と同じ量の文字が毎回の保存と送信に乗るのを避ける。読むのは Files から)。
- **再生**: 添付チップのモーダル(`FileItemModal`)が `audio/*` を `<audio controls>` で出す
  (録音に限らない)。MediaRecorder の webm は長さを持たず `duration` が Infinity になるので、
  末尾へ一度シークして確定させている。利用者が自分で聞き直せることが、モデルには気付けない
  誤り(「14件」→「4件」)への一番確実な確認手段。

#### ビットレートの実測(2026-10-03)

置き場所: `,/dictation/`(書き捨て。`bitrate.py` / `mr_bitrate.py` と `out/`)。
`,/voice-cut-exp/audio/wav/` の日本語音声 31 本(TTS 25 本 = 2 話者 × 話速、人の朗読 6 本。
1 本 30〜90 秒)を libopus mono で再エンコードし、本番と同じ設定(large-v3-turbo / int8 / CPU /
beam 5 / VAD / ja)で **1 本通しで**転写した。

| | 無圧縮 wav | 24 kbps | 16 kbps | 12 kbps |
| --- | --- | --- | --- | --- |
| CER(原稿比)平均 — TTS 25 本 | 4.03% | 3.48% | 5.10% | 3.10% |
| CER(原稿比)中央値 — TTS 25 本 | 2.89% | 2.31% | 2.89% | 2.60% |
| wav より 0.5pt 超悪い / 良い — TTS 25 本 | — | 7 / 8 | 7 / 7 | 7 / 9 |
| wav の転写からのずれ 中央値 — 朗読 6 本(原稿なし) | — | 2.73% | 3.65% | 5.43% |
| 同 5pt 超のずれ — 朗読 6 本 | — | 1 | 2 | 3 |

- **ビットレートによる精度の差は出ていない**(TTS)。圧縮した方が良い本数と悪い本数が同じで、
  差は Whisper 自体の揺れ — 1 分の音声を通しで転写すると、入力がわずかに違うだけで結果が変わり、
  ときどき末尾で幻聴ループに入る(16kbps の平均を上げているのは 1 本の幻聴 +42pt。32kbps でも
  8 本中 1 本で +30pt)。
- 朗読では 12kbps だけ wav の転写からのずれが大きめ(原稿が無いので良し悪しは不明、6 本)。
- **24kbps を採用**: 「差が出ない最小」は実測上 12〜16kbps だが、朗読の傾向と、これが読み直し用の
  原本であること、サイズが制約にならないこと(下)から 1 段上に倒した。
- **Chrome の実ファイル**(60 秒、fake マイク): 指定 32k → 28.5kbps / **24k → 21.6kbps** /
  16k → 14.8kbps / 12k → 11.1kbps / 指定なし → 125kbps。指定の約 9 割で、守られる。
  24k は毎秒 約 2.7KB = 60 分で約 9.7MB、**25MB に約 160 分**。
- **末尾は壊れていない**: ffmpeg 7 / 8 が全体 decode の最後に 1 回出す
  `Error parsing Opus packet header` は、ffmpeg 自身が libopus で作った webm でも出る(EOF の
  flush 時のもの)。`stop()` で止めても track 停止で止めても同じで、全パケットが decode できる。
  ただし上のとおり `stop()` した瞬間の 40〜50ms は入らない。
- **区間の時刻は合っている**: 添付の `start_sec`〜`end_sec` を ffmpeg で切り出して転写すると、
  その区間の `text` と一致した(分割の境界の前後の区間を含む)。

**未確認**: 実マイク(日本語の口述)/ Safari・Firefox(`audio/mp4` になるブラウザで
`audioBitsPerSecond` が守られるか、`<audio>` の長さの確定)/ モバイル幅 / 60 分の実録音
(分割は定数を 30 秒にして確認した)。

### 配備ごとの調整(env 専用、2026-10-03)

マイク・部屋の雑音・CPU の速さで調整が要る値だけを環境変数に出している(ken 決定:
「ある程度精度を決めるような設定は環境変数でいじれるように。細かくは作らない」)。**env 専用** —
配備の設定ファイルで決める値なので `RuntimeConfig`(DB 保存)にせず、管理画面にも利用者設定にも
出さない(`WHISPER_MODEL_DIR` と同じ素の env。変えたらサーバ再起動で反映)。
`nucllei/config.py::env_number` が読み、**非数・範囲外は既定に落として起動ログに warning 1 行**。
上の 4 つは `/api/config` の `audio.stt`(`segment_seconds` / `segment_pause_ms` /
`silence_threshold_db` / `recording_bitrate_kbps`)で録音バーへ渡る。録音バーは録音開始時に
1 度だけ読み、応答に無ければ同じ既定値を使う。

| 環境変数 | 既定 | 範囲 | 意味 | いつ動かすか |
| --- | --- | --- | --- | --- |
| `AUDIO_STT_SEGMENT_SECONDS` | 12 | 4〜30 | 区切りの目安秒(SOFT)。過ぎたら次の息継ぎで切る。強制切り(HARD)は **+ 4 秒で固定** | 短くすると表示は早くなるが破綻が増える(8 秒で約 2 倍、4 秒で約 4 倍 —「周期の実験」の表)。遅い話者には長い方が安全(8 → 12 秒で 1.44 → 0.32 件/分)。16 秒は 12 秒より良くならず遅れだけ増えた。転写 1 回(CPU で 4〜6 秒)より短い周期はキューが溜まる |
| `AUDIO_STT_SEGMENT_PAUSE_MS` | 400 | 100〜2000 | 息継ぎとみなす無音の長さ | 短くすると強制切りが減る(300ms で 19% → 8%)が、語中の無音(150ms 未満)に近づき語の途中で切れやすくなる — その害は未測定。強制切りが多い現場では、先に下のしきい値を見る |
| `AUDIO_STT_SILENCE_THRESHOLD_DB` | -45 | -90〜-10 | 無音判定のしきい値(AnalyserNode の `minDecibels`。これ未満は無音) | **マイクの音量次第**。実験では入力を -10dB 下げると強制切りが 19% → 3% に減り、-20dB では何も録れなかった。発話が拾われない(バーが「発話を待っています」のまま)なら下げる。雑音で息継ぎが無音にならず強制切りばかりになるなら上げる |
| `AUDIO_STT_RECORDING_BITRATE_KBPS` | 24 | 8〜128 | 通し録音(添付に残す原本)のビットレート | 12〜24kbps で転写精度の差は出ていない(「ビットレートの実測」)。上げるとサイズが比例して増え、添付上限から逆算する分割の間隔が短くなる |
| `WHISPER_BEAM_SIZE` | 5 | 1〜10 | 内蔵 faster-whisper の beam size(外部 STT には効かない) | 遅い CPU で転写が周期に追いつかないときに下げる(速くなる代わりに精度が落ちる)。**値を変えた実測はしていない** |

- 進捗バーの全長(HARD)と目盛り(SOFT / HARD)は目安秒から導くので、設定に追従する
  (実機: 目安 6 秒で目盛り 60%・息継ぎあり音声は約 6.5 / 7.1 / 6.5 秒・切れ目なしは 10.0 秒で切れた。
  既定は目盛り 75%・13.7 / 12.7 秒・16.0 秒。Playwright で `/api/config` の応答を書き換えて確認、
  `,/voice-env/check_env.py`)。
- しきい値を -30dB 以上にすると `minDecibels` が `maxDecibels`(既定 -30)以上になって例外になる
  ので、録音バーが上側を「しきい値 + 15dB」まで広げる(音の有無は bin が 0 を超えるかだけで見る
  ので判定は変わらない)。
- 通し録音の分割間隔の見積り(毎秒のバイト数)はビットレートの 9 割で計算する(Chrome の実測比)。
- **変数にしていないもの**: 強制切りの + 4 秒 / 60 分分割 / 利用者設定の「読み取り猶予」
  「最短の発話区間」。

### 読み取り猶予(`$settings.voiceSilenceTimeout`)

無音がこの長さ続いたら発話の区切りとみなす。**既定 4000ms**
(旧ハードコード 2000ms は「喋りながら考える」人には短すぎる — ken 指摘。
上限側は Call の応答遅延に直結するので 3〜5 秒レンジの中央を採った)。
UI は **Settings > Chats > Voice**(0.5〜30 秒、秒で入力し ms で保存)。
**録音バーと Call オーバーレイの両方**が読む(Call の `2000` ハードコードは撤去済み)。

同じ設定群に **`$settings.voiceMinChunkDuration`(既定 300ms)** —
これより短い区間は精度が落ちるので転写に送らない。測るのは**発話区間の長さ**
(最初に音を検出した時刻 → そのセグメントで最後に音を検出した時刻)であって、
録音していた実時間ではない。無音カットの `stop()` は `最後の音 + silenceTimeout` に来るので、
実時間で測ると必ず `silenceTimeout` 以上になり、既定値の関係(4000 > 1000)で
**判定が常に真になって効かない**(2026-09-05 修正。それ以前は咳払いや物音でも
1 セグメント転写に飛び、Whisper のハルシネーションが入力欄に入っていた)。
この修正で**初めて実際に効く**ようになったため、**既定を 1000ms から 300ms へ下げた**
(2026-09-05)。1000ms のままだと「はい」「うん」のような相槌が丸ごと落ちる —
ken の方針は「読み取り猶予は長めに = 話者を途中で切らない」なので、
**利用者の発話を落とすより、物音由来のノイズを許す**側に倒す。300ms は咳払い・
ドアの音のような単発の物音を落としつつ短い返事を残す妥協点で、根拠のある閾値では
ないので、配備で実測して動かしてよい(UI の範囲は 0〜5 秒、0 = 無効)。

### secure context ガード

`navigator.mediaDevices` は **secure context(https / localhost)でしか生えない**。
llens 実機は `http://<内部IP>/` 配備なので、無ガードだとマイク/Call ボタンが
**トーストも出さずに無反応**になる(getUserMedia 呼び出しで例外)。
`MessageInput.svelte` / `CallButton.svelte` はボタンを押せない見た目にしてツールチップで理由を出し、
押した場合もトースト(`Microphone requires a secure (HTTPS) connection.`)を出す。
`VoiceRecording.svelte` / `CallOverlay.svelte` の getUserMedia 直前にも同じガードを置く。
**`ENABLE_AUDIO_STT=false` の非表示とは別物** — あちらは「この配備に機能があるか」、
こちらは「このブラウザ経路で使えるか」。

### アップロードの MIME(`audio/webm`)

FE は長らく `recording.wav` / `type: 'audio/wav'` の**偽装ラベル**で送っていた
(MediaRecorder の実体は Chrome/Edge = webm/opus)。`routers/audio.py` の許可リストと
拡張子マップに `audio/webm` を足し、FE は `MediaRecorder.isTypeSupported` で
`audio/webm` → `audio/ogg` の順に選んで**実際の MIME をそのまま送る**。
Safari の MediaRecorder は `audio/mp4` しか作れないので、**`audio/mp4` も許可リスト +
拡張子マップに入れてある**(2026-09-05。入れる前は Safari / iOS が 400 になっていた —
偽装をやめた #56 からの回帰)。mp4 音声は非アクティブ形式なので
GHSA-m8f9-9whg-f4xr の「拡張子はサーバ側で決める」方針とは矛盾しない。
FE 側は `isTypeSupported` で webm → ogg の順に選び、どちらも使えなければ
ブラウザ既定(Safari = `audio/mp4`)に任せて実 MIME をそのまま送る。

## 並列モデル — どの層で直列化されるか(STT 内蔵経路)

1. **サービング層**: route は sync def / to_thread → AnyIO threadpool(既定 40 本)。
   並列リクエストの受付上限はここ。
2. **モデル層**: `WHISPER_NUM_WORKERS`(既定 1)= CTranslate2 のワーカー数。
   **1 のままだと同時文字起こしはモデル内で直列化**(スレッドは並んで待つだけ)。
   CTranslate2 は推論中 GIL を解放するので >1 で真のスレッド並列になる。
3. **演算層**: `WHISPER_CPU_THREADS`(既定 0 = ライブラリ既定)= 1 本の文字起こしの
   intra-op スレッド数。既定値は環境依存(OMP_NUM_THREADS 等)で、
   **強い CPU を使い切る保証がない — 本気運用では明示指定**。

総使用スレッド ≈ `NUM_WORKERS × CPU_THREADS`。強い CPU での目安:
ディクテーション主体なら `CPU_THREADS` = 物理コアの 1/2 程度から実測、
`NUM_WORKERS` = 同時発話者数の見込み(2〜4)。実測ベンチは未実施(#12 スモークと同時にやる)。
env 変更の反映は再起動(モデル再ロードは起動時 lazy と STT config 更新時のみ)。

## GPU を含むスケール路線(広く見据えた整理)

- **路線A: 内蔵 + CUDA** — `DEVICE_TYPE=cuda` で配線済み。`WHISPER_COMPUTE_TYPE` は
  float16 / int8_float16 へ(int8 既定は CPU 向け)。cpu_threads は無関係になる。
  欠点: **web プロセスが CUDA コンテキストを抱える**(VRAM 常駐・再起動の重さ・依存)。
- **路線B: 外部 OpenAI 互換 STT サーバ(本命)** — TTS bridge と同型の別コンテナ
  (speaches(旧 faster-whisper-server)等)を立て、`AUDIO_STT_ENGINE=openai` に切替。
  **fork はコード変更ゼロ**、ハード増強(強 CPU でも GPU でも)は STT コンテナの都合に閉じる。
  GPU 本気運用はこちらを既定路線とする。
- どの路線でも**内部 API(sync)の形は不変**: 内蔵推論は CPU/GPU とも呼び出しスレッドを
  ブロックする同期 API、外部エンジンは network I/O — いずれも「スレッドに逃がす」が正解で、
  caller(tool/filter)のコードは書き換え不要。async 化はここでは利得がない
  (CPU/GPU-bound には無力、低〜中並列の I/O では threadpool と差が出ない)。

    `{target=_self}` / 無指定 = 新規タブ(allowlist は target / download のみ)。
  - **埋め込み再生**: 生 HTML `<audio controls src="/api/v1/files/{id}/content"></audio>` を
    DOMPurify(`sanitizeChatHtml`、autoplay は FORBID_ATTR)経由で許容。video も同様。
    判断根拠: レンダラの「HTML を作らない」規律は**機械構造**(reasoning/tool_calls)の話で、
    モデル・tool 著の**コンテンツ** HTML は DOMPurify の柵内で従来から許容(画像・iframe 特例と同列)。
    markdown-it-html5-embed / block-embed は不採用 — renderer ルール型は lex()(トークン変換)経路で
    無反応、ruler 型は独自トークンがコンバータで落ちるため、導入しても配線コストは自前実装と同額。
    素の `<audio>` の方がモデルの既知度も高い。カスタム UI(波形等)が要る時は lexer 段の
    自前トークン化で置換可能(書式は不変のまま移行できる)。
  - `/content` は audio/* / video/* を **inline 配信**(attachment だと Firefox が再生拒否 —
    routers/files.py、保存導線は `?attachment=true` と `{download}` リンク)。
  - prism 層(prism-hu/llens)は skill 遅延ロード化済み: `nucllei/skills/audio.md`
    (tool_ids: audio_tools)で preset には skillIds で紐づけ、音声の指示が要るときだけ
    context に載る。tool の戻りはプレイヤー埋め込み + {download} リンクの 2 行
    (モデルが本文に貼る契約)。
  - **将来(#88)**: 「モデルに貼らせる」契約は tool のユーザー向け表示チャネル(display)
    確立後にそちらへ差し替え検討(tool が自分で表示すれば約束が構成的に真になる)。
