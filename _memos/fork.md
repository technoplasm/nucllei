## 0. この文書の目的

Open WebUI を基点とした自己ホスト型 LLM チャット製品「llens」の fork 開発にあたり、
**何を残し、何を捨て、何を作り直すか** の判断基準を、機能要件レベルで固定する。

エージェントはこの文書を、実装判断（機能の維持/削除/リファクタ）の一次根拠として扱うこと。
個別の実装で迷った場合、本文書の「要件区分」に照らして判断する。

## 2. 機能要件の区分

要件を4区分に分類する。エージェントはこの区分を実装判断の基準にする。

| 区分 | 意味 | 実装方針 |
|---|---|---|
| **CORE** | 製品の存在意義。デグレ厳禁。 | 最優先で維持・保護。テストで守る。 |
| **KEEP-MINIMAL** | 必要だが最小限でよい。過剰な追従は不要だが、デグレは困る。 | 動く状態を維持。upstream追従は慎重に。 |
| **DROP** | 不要。オマケ機能。自前で作れる/業務オンプレに不要。 | 削除または無効化を検討。少なくとも投資しない。 |
| **CONSTRAINT** | 横断的な制約条件。 | 全実装が従う。 |

## 3. CORE 要件（製品の核・デグレ厳禁）

### 3.1 ユーザー認証

- 自己ホスト環境でのユーザー認証を維持する。
- オンプレ病院イントラを想定。外部 IdP 依存を前提にしない（あってもよいが必須にしない）。
- 認証は「誰がログインできるか」の層。次項の認可（権限）と明確に分離して考える。

### 3.2 Filter 機能（inlet / outlet）

- **これが本製品の最重要資産のひとつ。** Open WebUI の inlet/outlet Filter（リクエスト前処理・レスポンス後処理を Function として差し込む機構）を **完全に維持する。**
- 用途: 患者フリーテキストの de-identification 前処理、TTS 注入、ログ加工など、
  **全リクエストに自動で挟まる中間層** としての役割。
- 代替製品（LibreChat 等）にこの機構が無いことが、fork を選ぶ主要根拠のひとつ（§7参照）。
- **判断基準**: Filter の実行モデル（inlet→LLM→outlet のパイプライン）を壊す変更は入れない。
  de-id / TTS / ログの各処理は、可能な限り **OWUI 非依存の独立ミドルウェアとして切り出し**、
  将来別基盤へ載せ替え可能な形に整理する（移植性の確保）。
- **適用スコープの改訂（2026-07-07、#46）**: 「全リクエストに自動で挟まる」は upstream の
  is_global（全モデル強制）機構による挙動だったが、制御面の二重化を嫌い **per-model 割り当て
  （モデルの `filterIds`）一本に統一**した（global / active 撤去）。実行モデル自体は不変。
  帰結として **de-id 等の全科共通 Filter は各 preset モデルに割り当てる運用**になる
  （llens はモデル数が少なく管理可能という判断）。新規 preset へ付け忘れると de-id が挟まらない点に注意。

### 3.3 Tool / Skill 単位のグループ権限（認可）

- **これが fork を選ぶ最大の根拠。** Tool および Skill を、**group 単位でアクセス制御** できる機構を維持・強化する。
- 要件の本質は **二軸の権限モデル**:
  - 横軸: 診療科（内科 / 外科 / 看護部 …）
  - 縦軸: 職位（部長 / 一般 / 研修医 …）
  - この **交差（診療科 × 職位）** でスキルの可視性を出し分ける。
- ユーザーは複数 group に所属可能。「内科 かつ 部長」に特定スキル、という交差割り当てを表現できること。
- **運用主体は事務**: 非技術の事務担当が、システム管理画面（GUI）から group とツール/スキルの割り当てを運用する。
  → 管理 UI を CLI や設定ファイルに退行させないこと。**GUI での group×tool 割り当て運用を維持する。**
- 実装上の注意: group 設計は交差が増えると複雑化するため、
  **診療科 group と職位 group を分離し、スキル側で必要な交差を定義する** 設計を推奨（命名規則を用意する）。
- **改訂(2026-07-10、#4 close / #66)**: 交差(AND)条件の専用機構(llens 拡張 `group_terms`)は
  **撤去**した。ユーザーは複数 group に所属でき権限は OR 合成なので、「内科 かつ 部長」は
  「内科部長」group を 1 つ作って割り当てれば表現できる — ACL 側に AND 演算を持つ必要が
  なかった(前提誤り)。二軸の運用要件自体は group の命名・分割で満たす。
  権限モデル全体の真実源は `_memos/permissions.md`(3層: admin / skill editor / user)。

### 3.4 モデル接続（OpenAI 互換）

- **OpenAI 互換エンドポイントであれば何でも接続できればよい。** これが唯一のモデル要件。
- 北大では vLLM / ローカルサーバ経由の OpenAI 互換 API を想定。
- 特定プロバイダ固有機能（Ollama 専用機能など）への依存は増やさない。接続は OpenAI 互換を主軸とする（Ollama 接続自体は残す）。
- 最小構成: OpenAI 互換 `base_url` を接続要件とし、ワークスペースでモデル(system prompt 込み)を1つ作ればチャットできる状態を保証する。
- 接続由来の生モデル(Ollama/OpenAI が列挙するベースモデル)はピッカーに出さない。使えるのはワークスペースで作ったモデルだけ(`/api/models` が Models テーブル行なしを除外、535da68e9)。

## 4. KEEP-MINIMAL 要件（最小限でよい・デグレは困る）

### 4.1 TTS（音声合成）

- **最小限あればよい。** 日本語 TTS（VOICEVOX / AivisSpeech 系、`voicevox-openai-tts` ブリッジ経由の OpenAI 互換 TTS）が動く状態を維持。
- 過剰な TTS 機能追加は不要。ただし **既存の日本語 TTS 連携をデグレさせないこと。**
- オフラインバンドル構成を壊さない（air-gapped 配備があり得るため）。

### 4.2 STT（音声認識）

- **最小限あればよい。** 基本的な音声入力が動けば十分。
- 高度な STT 機能への投資は不要。デグレは避ける。

**KEEP-MINIMAL 全体の方針**: upstream の TTS/STT 周辺が大きく変わっても、無理に追従しない。
「今動いているものが動き続ける」ことを優先し、新機能追従より安定を取る。

## 5. DROP 要件（不要・投資しない）

以下は業務オンプレの薄い製品には不要。**削除または無効化を検討し、少なくとも開発リソースを割かない。**

- **RAG（組み込み文書検索）**: 不要。必要なら自前で作れる範囲。組み込み RAG の追従・拡張はしない。
- **組み込みツール類（内蔵の Web 検索・画像生成等のオマケ）**: 不要。オマケ的機能であり、必要なものは自前実装する。
- **メモリー機能（会話をまたぐ記憶）**: **不要。** 業務用オンプレ想定であり、ユーザー横断の記憶は要件に反する場合すらある。無効化を検討。（→ #67 で機能・テーブルごと撤去済み 2026-07-10）
- その他、汎用製品として不要な「全部入り」的機能全般: 投資対象外。

**判断基準**: 「これは自前で作れるオマケか？」「業務オンプレに本当に要るか？」で迷ったら DROP 側に倒す。
コアは薄く保つ。

## 6. CONSTRAINT（横断的制約）

- **オフライン完結（必須機能について）**（2026-07-17 改訂、旧「air-gapped / オフライン前提」）: 配備先は一様でない —
  基本はオンプレで、air-gapped（完全閉域）の環境も外部ネットワークに出られる環境もある。外部ネットワーク前提の機能を
  必須にせず、オフラインバンドル可能であること。**閉域・オンプレを理由にオプショナルな外部連携を切らない。**
- **コード実行サンドボックス**: 既存の nsjail + IPython サンドボックス構成を尊重する（Pyodide には戻さない）。
- **移植性の確保**: de-id / TTS / ログ等の Filter 処理は、可能な限り OWUI 非依存のミドルウェアとして切り出し、
  将来 llens が別基盤に載る場合でも持ち運べる形にする。
- **ライセンス基点固定**: 本 fork は特定タグ（例: v0.6.5）を基点とし、
  それ以降の upstream コミットを無条件にはマージしない（帰属・条項の詳細は調整中のため、混入を避ける）。
  upstream から取り込む場合は **ファイル/コミット単位で選択的に** 行い、取り込み由来を記録する。

## 7. fork 根拠のまとめ（なぜ移行ではなく fork か）

他基盤（特に LibreChat）への移行ではなく、Open WebUI の fork を選ぶ根拠は、
**運用資産が CORE 要件に集中しており、他基盤ではそれらを作り直す必要があるため。**

| 要件 | OWUI fork | 移行（LibreChat 等） |
|---|---|---|
| inlet/outlet Filter（de-id/TTS/ログ） | あり（維持できる） | 相当機構なし → 自前ミドルウェア実装が必要 |
| Tool/Skill の group 権限（診療科×職位） | ネイティブに GUI 運用可 | RBAC が弱い/開発途上 → 自前 RBAC 実装が必要 |
| 事務による GUI 権限運用 | 既存の管理画面で可 | 相当 UX を自作する必要 |
| OpenAI 互換モデル接続 | 可 | 可（差はない） |

→ 移行は「ライセンスの綺麗さ」1点のために **CORE 運用資産を作り直す取引** になる。
　したがって合理的な道は **fork 維持 + ライセンス問題の個別処理**（基点固定等）。

## 8. エージェントへの実装指示（要約）

1. **CORE（認証 / Filter / group権限 / OpenAI互換）を最優先で保護する。** これらのデグレは製品価値の直接毀損。
2. **DROP（RAG / 組み込みツール / メモリー）には投資しない。** 削除・無効化で薄いコアを保つ。
3. **KEEP-MINIMAL（TTS/STT）は「動き続ける」ことを優先。** 新機能追従より安定。
4. **迷ったら「薄い業務オンプレ基盤」の北極星に照らす。** リッチさより、統治とパイプラインの堅牢さ。
5. **de-id/TTS/ログ の Filter 処理は独立ミドルウェア化を志向し、移植性を確保する。**
   （→ 2026-07-17 #13 close: 処理本体は prism 層の管轄と確定。fork 側は差し込み口
   = Filter パイプラインの堅牢さに専念）
6. **upstream の無条件マージ禁止。** 取り込みは選択的・記録付きで。
7. 帰属・ライセンスの組織的詳細は調整中。**本文書の技術要件の範囲で判断し、組織論には立ち入らない。**
8. **運用要件(病院要件)の確認・充足は llens(配備側)の仕事。nucllei は「それをカバーする
   土台があるか」だけを見る**(2026-07-21 確定、#74 / #31 close で適用)。
   バックアップ・保持期間・監査などの ops は fork の issue にしない。
   #13 close の「処理本体は prism 層・fork は差し込み口」と同じ線引きの運用版。
   - 監査の確定形(#31): 監査対象は**カルテ DB 等の外部記録系へ到達する tool**(= LLENS)で
     あり、nucllei 自身の操作(グループ編集等)は対象ではない。実体の記録は tool 側が行い、
     nucllei の土台は「tool への __user__/__chat_id__/__message_id__ 注入 + チャットの保全
     (content_blocks 永続化・soft-delete・#19 admin 直参照)」で充足済み。upstream の
     HTTP 監査ミドルウェアは撤去した(667860ed9)。
