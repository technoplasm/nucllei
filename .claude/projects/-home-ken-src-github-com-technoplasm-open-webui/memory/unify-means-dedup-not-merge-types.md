endaaman の「一本化を好む / 意味のない仕様を足さない」は、**冗長・死んだ経路を1本に畳む**ことを指す。異なる種別(文書抽出 / STT / TTS など)を無理に共通シグネチャへ統一することは含まない — 種別で入出力も追加オプションも違うなら別々の内部API のままでよい。

**Why:** #52 file-handling で `extract(file_id, provider)` に全種別を一本化する案を出したら却下された。「hook 内で呼び分けるから入口は同じである必要がない。種別で追加オプションが違うので無理に合わせる必要がない」。統一の抽象化はしばしば意味のない仕様の追加になる。

**How to apply:** 複数種別を1関数に畳む設計を提案する前に「これは冗長の除去か、異種の強制統合か」を自問する。後者なら素直に種別ごとに1本ずつ用意し、呼び分けは上位(hook/filter)に委ねる。加えてこれら内部関数は builtin tool(#18)としてモデルにも露出させる方針。詳細は `_memos/file-handling.md` プランB節。
