# スキルの遅延ロード

この文書は、nucllei がスキルとツールを**必要になったときだけモデルに見せる**仕組み
(遅延ロード) の説明です。応答の中に「Toolの使用 **load_skill**」というブロックや
「ツールを読み込みました」という札が出てくるのは、この仕組みが働いているからです。

ツール・スキル・拡張そのものの違いは「ツール・スキル・拡張の違い」にあります。

## なぜ全部を見せないのか

モデルに渡せる文章の量 (コンテキスト) には上限があり、**使えるツールの説明はすべて毎回のリクエストに載ります**。
モデルに割り当てたツールを増やすと、その分だけ会話に使える余地が減ります。
選択肢が多いほどモデルが選び間違えやすくもなります。

そこで nucllei は、スキルに紐づけたツールを**最初は載せず**、そのスキルが読み込まれた時点で
初めてモデルに見せます。ふだんは軽く、必要になった作業のときだけ道具が増える、という形です。

- **モデルに直接割り当てたツール** — 毎回載ります。常に使う道具はこちら。
- **スキルに紐づけたツール** — そのスキルが読み込まれるまで載りません。特定の作業でだけ使う道具はこちら。

## 何が起きているか

### 1. ふだんモデルに見えているのは 1 つの窓口だけ

そのモデルに割り当てられたスキルは、**`load_skill` という 1 つの窓口**にまとめられて
モデルに提示されます。窓口の説明の中に、スキルの一覧が

```
- スキルID: そのスキルの説明
- スキルID: そのスキルの説明
```

という 1 行ずつの形で入っています。**手順書の本文は、この時点では渡っていません。**

### 2. モデルが「これだ」と判断して読み込む

モデルは説明の行を読み、必要と判断したスキルの ID を指定して `load_skill` を呼びます。
このとき、

- スキルの**本文 (手順書)** がモデルに返されます。
- そのスキルに**ツールが紐づけてあれば、そのツールがここで初めてモデルに追加されます**。

### 3. 次のやり取りから、そのツールを呼べる

追加されたツールは、そのやり取りの続きからモデルに見えるようになります。
モデルは読み込んだ手順書に従い、新しく使えるようになったツールを呼んで作業を進めます。

## 利用者から見て何が起きるか

応答の中に折りたたみのブロックが現れます。

| 見えるもの                                           | 意味                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------ |
| 「Toolの使用 **load_skill**」                        | スキルを読み込んだ、というブロックです                                         |
| ブロックを開いた中の本文                             | 読み込まれた手順書そのものです                                                 |
| その下の「**ツールを読み込みました**」の札とツール名 | そのスキルが連れてきたツールです。ここに並んだツールを、この先モデルが使えます |

**ツールを連れてこないスキルでは、この札は出ません。** 本文だけが表示されます。

利用者が入力欄の先頭で `/スキル ID` と打って起動した場合も、画面上は同じ形になります。
利用者が起動しても、モデルが自分で読み込んでも、同じ 1 つの経路を通るためです。

## 一度読み込んだら、その会話の間は有効

読み込んだスキルとそのツールは、**その会話の中では以降も有効**です。毎ターン `/スキル ID` を
打ち直す必要はありません。

有効かどうかは、そのつど会話そのものから導き直されます。したがって、

- **`/スキル ID` を打つ前のメッセージから枝分かれした枝では、そのスキルは効きません。**
- **起動したメッセージを削除すると、効かなくなります。**
- 同じスキルを重ねて読み込んでも害はありません (同じ結果になります)。
- 手順書の本文をあとから編集した場合、`/スキル ID` で起動した分については次のやり取りから
  新しい本文が使われます。一方、**画面に残っている過去のブロックの表示は書き換わりません**。

`{{CURRENT_DATE}}` のような差し込み変数は、毎回のリクエストで展開し直されます。`{{BASE_MODEL_ID}}` には、そのリクエストで選ばれているモデルのベースモデルの ID が入ります (変数の一覧は [13 スキル](13_skills.md))。

## 効く条件は 3 つ (すべて満たす必要があります)

スキルが働くのは、次の 3 つが**すべて**成り立つときだけです。

1. そのモデルの「能力」(Capabilities) で「**スキル**」がオンになっている
2. そのスキルが「ワークスペース > モデル」で**そのモデルに割り当てられている**
3. そのスキルが**自分に見えている** (公開、または自分・自分のグループが対象に入っている)

どれかが欠けると、`/スキル ID` と打っても**ただの文字として送られます** (エラーにはなりません)。
モデルへの一覧にも載りません。

## モデルはどうやって選ぶのか

**説明文だけが手がかりです。** モデルは一覧に並んだ `ID: 説明` の行を読んで、どれを読み込むかを決めます。
中身は読み込むまで見えません。ここから次の帰結が出ます。

- **「説明」が空のスキルは一覧に載りません。** モデルからは存在しないのと同じです
  (利用者が `/スキル ID` で起動することはできます)。「ワークスペース > モデル」の
  スキル割り当ての欄では、説明が空のスキルに「(説明なし)」と黄色で注記が付きます。
- **説明が曖昧だと呼ばれません。** 「何をするか」だけでなく、**「利用者がどう言ったときに使うのか」**を
  書くと選ばれやすくなります。想定される言い回しや語を説明に含めるのが有効です。
- 逆に、説明が広すぎると関係ない話題でも読み込まれます。

同じことがツールにも当てはまります。ツールでモデルが読むのは**関数に書いた説明 (docstring)** で、
一覧画面の「説明」欄ではありません。

## つまずきやすいところ

- **スキルは読み込まれたのに、そのツールが使われない** — スキルにツールが紐づいているかを
  確認します。ツールを紐づけたスキルの作成・更新は**管理者だけ**の操作です。管理者以外が
  作ったスキルにはツールが付いていません。
- **`/スキル ID` を打ったのに何も起きない** — 上の「効く条件は 3 つ」を順に確認します。
  条件を満たさない場合、エラーは出ずにそのまま文字として送られます。
- **モデルがスキルを読み込んでくれない** — 「説明」が空でないか、説明にその話題の語が
  入っているかを見直します。それでも確実に使わせたいときは、利用者が `/スキル ID` で明示的に起動します。
- **スキルは効いているのに、話が進むと道具が減ったように見える** — 会話を分岐させたり、
  起動したメッセージを消したりすると失効します。分岐した枝では打ち直してください。
